# Create a cylinder prop in the editor

Open the model package panel and enable **Create cylinder package**. Enter a radius, height, segment count and portable `.cylinder.json` asset identity. Choose a license text file, a new package destination, package name and version, then acknowledge redistribution rights and create the package. This path needs no external model file. Install the result, preview it in the package browser, and assign it as a static Room prop through the normal model-binding workflow. Binding Undo/Redo, Save and reopening retain the generated geometry.

The generator creates a Y-up capped cylinder centered around the origin, with three primitives and separate material slots for its side, top and bottom. It supplies outward winding, side radial normals, hard cap normals and UVs. Radius and height must be finite original f64 values in `[0.001, 1000000]`; allowed segment counts are `8`, `16`, `32`, `64` and `128`. These inputs are checked before binary32 geometry conversion. The existing fixed circle table and offline producer are reused without a new renderer or simulation schema.

The package contains ordinary static `model.orrmodel` and license metadata, with models-only capability. Its model identity is the entered `.cylinder.json` path, and `$source` provenance hashes the exact generated five-field recipe. The recipe format remains `orr_static_model_cylinder`, version `1`, with `radius`, `height` and `segments`. Source-model paths are not inspected or read during creation. Parameters are a draft for a new immutable output; this does not edit an installed package or generate a collider. Collision and entity placement remain separately authored.

License acknowledgement, package validation, safe local paths and new-only publication use the existing package rules. Invalid geometry inputs, unsupported license data or an existing destination fail without replacing prior content. Context changes reject adoption of a stale result. Consent is revoked by draft or project-context changes, and a completed result is accepted only once for the current creation context. An already dispatched worker can finish publishing a new package after a context change; stale results are not adopted, and the output is retained at its reported location. The supplied license is metadata rather than a rights determination.

Focused acceptance covers independent cylinder geometry/topology/UV and normal expectations, all segment choices, strict recipe and numeric bounds, source-less publication, real creation widgets, installation/browser use, binding history, Save/reopen and Room CPU use. Linux CPU/strict-feature checks do not establish Windows execution, physical GPU/window rendering, native game export or actual play/video.
