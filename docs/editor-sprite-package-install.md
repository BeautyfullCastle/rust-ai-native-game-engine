# Preview and install a local sprite package

The Sprite panel can preview and explicitly install a local sprite package into the project named by the open bindings sidecar. The backend and panel UI are default-off behind `sprite-package-install`; `sprite-grid-authoring` also enables this feature when the PNG-grid creator is wanted. See [Create a sprite package from a PNG grid](editor-sprite-grid.md) for that optional creator.

Open matching local Arena or Collect bindings in Edit mode, expand **Install local sprite package**, and enter the package directory on the same machine. **Preview sprite package install** reads the source and project lock, then shows the package summary without changing the project. Installation is enabled only when the preview describes one new direct package. Click **Install previewed sprite package** to activate that preview.

The package must declare exactly the `sprite` capability, have no dependencies, and contain only `sprites.json`, `LICENSE.txt`, and the atlas image named by the sprite document. The document, PNG and nonempty UTF-8 license are validated before preview. Files are bounded (4 MiB document, 16 MiB PNG and decoded RGBA, 64 KiB license). The package name must be absent from both direct selections and dependency packages; this workflow cannot replace or upgrade an existing name. Paths must be absolute, normalized local paths with trusted ancestry; linked or reparse ancestry and remote host paths are refused. These checks assume stable local ancestry and are not a race-proof filesystem sandbox.

After a successful install, the existing Sprite panel workflow remains explicit. Enter the package name and document path, click **Load sprite document**, choose a region or clip, select the scene entities, and click **Assign sprite to selection**. Installation does not load the new document or assign it. Bindings **Undo/Redo** and **Save bindings** act on the sidecar; scene Save and scene history are separate. The install itself does not change bindings, scene state, editor history or the already loaded texture cache.

Changing the package-directory field or the bindings, scene or editor context invalidates an already prepared plan or discards a late preview result. Changes to manifest fields, declared file-content hashes or semantic entries in the active lock after preview succeeds are detected only when you click **Install**; a mismatch refuses the commit and consumes the plan. Whitespace or layout changes to the manifest or lock JSON do not invalidate the preview. After a semantic mismatch, correct the input and preview again. A refused or failed commit keeps the package inactive; the checked writer may have staged immutable content objects that the active lock does not reference. Inspect the project lock before retrying. Do not treat an object in the cache as an active package or automatically delete/retry after a failure.

Focused CPU checks and a headless egui harness do not establish native window or GPU rendering. Windows execution and actual play/video remain unverified until separately exercised.
