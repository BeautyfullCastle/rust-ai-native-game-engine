# Mesh scene lighting

The optional `mesh-navigation` editor workflow stores renderer lighting beside a saved MeshNavigation scene in `<scene filename>.mesh-lighting.json`. Lighting is view metadata: applying or saving it does not patch the scene, alter the deterministic simulation, or create entities. With no lighting sidecar, the renderer keeps the existing shared viewport lighting from `orr_sample::yard3d_view::yard_lighting()`. The lighting form starts from that same policy, so applying its untouched values does not change the scene's appearance.

Open **Mesh game lighting** for controls covering the directional light, light/sky/ground colors, intensity, ambient strength, shadows and shadow coverage, tone mapping, and exposure. Changes remain a form draft until **Apply game lighting**. Apply/Undo/Redo use a bounded panel-local history; **Save game lighting** persists the selected state, and removal requires explicit confirmation. Unsaved form/history changes and invalid or stale sidecars block Play and export until resolved.

The sidecar is strict schema 1 JSON with the `ORR_MESH_LIGHTING_V1` identity, exact scene filename, and admitted static-mesh graph revision. Reads and writes are bounded to 16 KiB and validate finite, bounded lighting values. It contains no package/model source paths or external assets. The UI targets a saved, writable local MeshNavigation scene with a coherent admitted graph; it does not expose lighting editing to remote or preview sessions.

Sidecar updates use bounded local-file checks, a prior digest, and final rechecks. This is optimistic change detection, not strict filesystem compare-and-swap or isolation from concurrent writers; use a trusted, stable local directory. No claim is made about protection from hostile concurrent filesystem mutation or power loss.

When the optional mesh-game export is enabled, a scene with lighting exports the scene, its lighting sidecar, the manifest, and the dedicated player. The exported player must advertise the `ORR_MESH_LIGHTING_V1` capability marker; legacy players are refused rather than silently ignoring lighting. Export is a separate explicit action and does not execute a selected player binary.

The opt-in hardware-Vulkan acceptance workflow exercises actual editor viewport pixels, local lighting Apply/Undo/Redo/Save, the **Duplicate mesh workspace…** flow, and a fresh Physics-editor reopen after the original workspace directory is hidden. It compares the duplicated scene and lighting-sidecar bytes with the originals, then checks Play/Stop without changing the scene checksum. Its optional `ORR_MESH_LIGHTING_OUTPUT` scene path must be inside the fixture's `source workspace` directory; the optional `ORR_MESH_LIGHTING_EXPORT_OUTPUT` bundle directory must remain beneath the newly created `ORR_MESH_LIGHTING_CAPTURE_DIR` fixture root. Optional bundle checks validate exact lighting bytes and manifest hashes. These checks do not constitute a native runtime launch unless a separate native receipt is recorded. They do not validate physical operating-system input.
